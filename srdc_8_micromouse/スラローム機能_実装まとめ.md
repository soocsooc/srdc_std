## 1. 追加した機能の全体像

- 従来の90度旋回 `rotate()` は「半区画減速 → その場超信地旋回 → 半区画加速」で、旋回のたびに実質ほぼ停止する
- 新しい `slalom()` は左右モータの速度差だけで**停止せずに**90度曲がる
- 探索アルゴリズムに組み込んだスラローム版 `lefthandSlalom()` / `adachiSlalom()` を追加（モード5・6）
- 行き止まりの180度Uターンもその場旋回ではなく「90度旋回→バック→前進」×2で縦横の位置を補正する `uTurn()` を追加
- 連続旋回・旋回直後の再加速・行き止まりUターンを一続きに確認できる調整モード `slalomSequenceCheck()`（モード7）を追加
- 4x4コースの最外周をスラローム→直進の繰り返しで周回し続ける調整モード `circuitCheck()`（モード3、元の単発90度旋回確認`slalomCheck()`を上書き）を追加
- `slalom()`に角度パラメータ（度単位、従来は90度固定）を追加し、直進を挟まない連続旋回では90度未満（`slalom_multi_angle`、暫定75度）に減らして横方向のズレを抑えられるようにした
- 既知の迷路情報を使う最短走行 `FAST::run()` のスラローム版 `FAST::runSlalom()`（モード7）を追加。90°旋回のみ`slalom()`に置き換え、180°（既知壁のみの経路では通常発生しない）と開始直後の方向合わせは`rotate()`のまま（本フォークで追加、2026-09-21）

### 2.2 無限ループバグの修正

- **症状**: `turn_diff` の下限が `0.0` だったため、減速切り替えタイミングの誤差次第で回転量 `turn_len` の増加が完全に止まり、2つ目のループ（`turn_len > obj_turn` 待ち）が無限ループになることがあった
- **修正**: `rotate()` が速度の下限を `MIN_SPEED` にしているのと同じ考え方で、`turn_diff` の下限も `0.0` → `MIN_SPEED` に変更。これにより回転が必ず進み続け、ループは必ず終了する
- 合わせて、無限ループ調査用に自分で追加していたデバッグコード（`switchGet()==1` での `return` 中断、確認用 `ledSet()`）を削除。**中断は `turn_enable`/`turn_diff` のクリーンアップをスキップしてしまい、以後の `rotate()` の動作までおかしくする副作用があったため、実運用で「曲がり切れない」の一因になっていた**

### 2.4 並進速度と旋回の同時制御（3回設計をやり直した）

同じ`turn_diff_max`設定で調整モード（開けた場所）では曲がり切れるのに、実際の迷路（通路幅の制約下）では曲がり切れない、という問題を軸に設計を3回見直した。

1. **案1（前後に別の直進区間で減速/加速）**: `slalom()` の前後に `straight()` で `search_speed→slalom_speed→search_speed` を挟む。→ 前後の直進区間の分だけ余計に進んでしまい、次の旋回に間に合わない・区画をはみ出す問題が発生
2. **案2（`slalom()` 内部で並進速度も同時に加減速）**: 追加の直進区間なしで `slalom()` 自身の中で減速・加速。→ `slalom()` が使える距離（`obj_turn`、片輪弧長で数十mm）が短く、特に直進直後の高速状態からその中だけで減速しきるのは距離的に無理があり、連続する同方向90度旋回で2回目が間に合わない問題が発生
3. **案3（現状）**: `slalom()` **前半だけ**内部で `entry_speed → slalom_speed` に減速し、**後半は再加速せず`slalom_speed`のまま**終了。加速するかどうかは呼び出し側に委ねる：次が直進なら `straight(SECTION, g_run.speed, search_speed, search_speed)` でその時点の実速度から加速し直す。次も旋回ならそのまま `slalom()` を呼び、連続旋回中は無駄な加減速をしない

実車での走行観察から「減速はスラローム中の方がスムーズ」「後半の再加速は連続旋回では不要」という2点のフィードバックを反映して案3に到達した。

#### 実コースでの走行距離調整（2026-09-18）

実車で4x4コース（1辺3区画=`SECTION*3`）を周回させたところ、当初の設計「角ごとに`straight(SECTION*3, ...) → slalom(right,1)`を単純に繰り返す」では、想定より曲がるタイミングがずれることが判明。

より正確には、`slalom()`による90度旋回は理論上の旋回位置（角の壁ぴったり）では起きない。**旋回そのものが理論上の旋回位置の0.25区画手前から始まり、0.25区画余計に進んでから終わる**（角を挟んで前後にはみ出す形になる）。実測では、`slalom()`終了時点で機体は角の壁から1.25区画進んだ位置におり、そこから1.5区画直進した位置（壁から2.75区画、＝次の角の壁の0.25区画手前）で次の`slalom()`を開始するのが実コースに合っていた。
これを踏まえて`circuitCheck()`を以下のように修正した（`adjust.cpp`、ユーザー側で実車調整して反映）。

```cpp
g_run.accelerate(HALF_SECTION, g_run.search_speed);
g_run.straight(SECTION * 2, g_run.speed, g_run.search_speed, g_run.search_speed);  // 最初の角だけ距離が異なる
g_run.slalom(right, 1);

while (switchGet() == 0) {
  g_run.straight(SECTION * 2.75, g_run.speed, g_run.search_speed, g_run.search_speed);  // 2周目以降の各辺
  g_run.slalom(right, 1);

```

- 2辺目以降は`straight(SECTION*2.75)`で統一（直前の`slalom()`終了位置を基準に、次の角の0.25区画手前で旋回を開始する計算）
- 合わせて`turn_diff_max`/`slalom_accel`も実車調整済み（§3参照）

### 2.9 真因判明：`RUN::slalom()`がパルスカウンタをクリアせずに返っていた(2026-09-18)

「旋回自体が理論上の旋回位置の0.25区画手前から始まり、0.25区画余計に進んでから終わる」という2.8の実測を踏まえて`run.cpp`を見直したところ、**この0.25区画のズレは純粋な旋回半径・軌道の問題ではなく、`slalom()`がパルスカウンタをクリアしないまま返っていたことが主因**と判明した。

`run.cpp`の各走行関数のカウンタクリア(`counterClear()`)の有無を整理すると次のとおり。

| 関数 | 開始時にクリア | 終了時にクリア |
| --- | --- | --- |
| `accelerate()` | する | する（末尾の`stay()`内） |
| `rotate()` | する | しない（末尾は`stop()`のみ） |
| `slalom()`（修正前） | する | **しない**（末尾は`stop()`も`stay()`も呼ばない） |
| `straight()` | **しない** | 条件次第（`finish_speed`≠`MIN_SPEED`なら`stay()`でクリア、`MIN_SPEED`なら`stop()`で未クリア） |
| `oneStep()` | **しない** | する（末尾の`stay()`内） |
| `decelerate()` | **しない** | しない（末尾は`stop()`のみ） |
| `moveFixed()` | する | しない（末尾は`stop()`のみ） |

`straight()`/`oneStep()`/`decelerate()`は自分の開始時にクリアしない設計になっている。これは`stay()`で等速のまま「考え中」に転がった分の距離を、次の走行関数の目標距離から自動的に差し引くための意図的な仕組み（`stay()`の項参照、マニュアルp.88）。つまり「直前の関数が呼び出し側にとって意味のある基準点でクリア済み」という前提の上に成り立っている。`rotate()`は開始時にクリアするので問題にならず（`decelerate→rotate→accelerate`の並びで、`rotate()`の後は必ず`accelerate()`が来て再クリアされる）、`accelerate()`/`oneStep()`は`stay()`経由で終了時に必ずクリアされる。

**`slalom()`だけがこの前提から外れていた**：開始時にはクリアするが、終了時は「速度を落とさず次につなげる」ために`stop()`も`stay()`も呼ばずに直接`accel`/`upper_speed_limit`等を書き換えて終わっていたため、カウンタは旋回中に溜まった生パルス値のまま残る。直後に呼ばれる`straight()`（開始時クリアなし）はこの残留パルスを「すでに走った距離」として引き継いでしまい、渡した`len`より実際の走行距離が短くなる。`circuitCheck()`で`SECTION*2.75`のような値が必要だったのは、この目減り分を経験的に打ち消していたため（狙って設計した値ではなく、結果的に辻褄が合っていた）。

**修正**（`run.cpp`）：`RUN::slalom()`の末尾に`counterClear()`を追加。これにより`slalom()`は「速度は落とさず、位置カウンタだけリセットして返る」関数になり、呼び出し側は`slalom()`の直後の`straight()`/`oneStep()`/`decelerate()`に**素の距離**（そこから何区画分か）を渡せばよくなった。

**各呼び出し元への影響**は次のとおり。

- `lefthandSlalom()`/`adachiSlalom()`（`search.cpp`）：`slalom()`の直後に`straight(SECTION, ...)`や`oneStep(SECTION, ...)`を呼んでいる箇所は、いずれも最初から「素の1区画」のつもりで`SECTION`を渡していた。今回の修正でその前提が正しく成立するようになったため、**コード変更は不要**（今まで`slalom()`直後の直進が実際には短く終わっていたバグが、この修正で解消される）
- `slalomSequenceCheck()`（`adjust.cpp`、モード7）：「旋回直後の直進」フェーズ（`slalom(left,1)`の直後の`straight(SECTION, ...)`）も同様に、これまで短く終わっていたのが修正で正しく1区画走るようになる。**コード変更は不要**
- `circuitCheck()`（`adjust.cpp`、モード3）：`slalom()`の直後の`straight()`の意味が「残留パルスを差し引いた距離」から「素の距離」に変わったため、**距離を再計算する必要がある**。2.8の実測（旋回そのものは理論位置の0.25区画手前〜0.25区画先を使う）から理論値を逆算し、初回`SECTION*2`→`SECTION*2.25`、2辺目以降`SECTION*2.75`→`SECTION*2.5`に変更した。その後ユーザー側で実車再調整し、`SECTION*2`（初回）／`SECTION*1.75`（2辺目以降）で確定（**circuitCheck()の調整完了**、2026-09-18）

### 2.10 連続旋回時の横ズレ対策：`slalom()`に角度パラメータを追加

- **症状**：`slalom()`のカウンタクリア修正（§2.9）後、`slalomSequenceCheck()`（モード7）の連続旋回フェーズ（直進を挟まず`slalom(right,1)`→`slalom(left,1)`）を実車で確認したところ、2回旋回した後の位置が横方向に0.5区画ずれていた。旋回前後の直進（助走の`straight()`、旋回直後の`straight()`）が影響していると推定
- **対策**：`RUN::slalom(dir, times)` の`times`（90度単位の整数倍のみ）を`angle`（度単位の`float`）に一般化し、90度未満の任意角度で旋回できるようにした。直進を挟まない連続旋回（右→左のS字クランクなど）では90度+90度だと横方向のズレが大きくなりすぎるため、呼び出し側で角度を減らして（例：80度×2）曲がることで横ズレを抑えられないか試す
- `run.cpp`：`obj_turn = tread_width * PI / 4.0 * times` → `obj_turn = tread_width * PI * angle / 360.0`（`angle=90`のとき従来の`times=1`と一致するよう度数から換算）
- 新パラメータ`slalom_multi_angle`（初期値80度→実車調整で75度、Web調整可能）を追加し、`slalomSequenceCheck()`の連続旋回フェーズで使用：`slalom(right, slalom_multi_angle)` → `slalom(left, slalom_multi_angle)`
- 単発の90度旋回（`lefthandSlalom()`/`adachiSlalom()`の通常旋回、`circuitCheck()`）は`slalom(dir, 90)`とリテラル値で呼ぶよう変更（`times=1`→`angle=90`への機械的な置き換え、動作は変わらない）
- **`lefthandSlalom()`/`adachiSlalom()`（実際の探索走行）には未適用**：これらは1区画ごとにセンサで判定する反応的なアルゴリズムのため、「次の旋回も連続するかどうか」を事前に知ることができず、`slalomSequenceCheck()`のように狙って角度を減らすには先読みロジックの追加が必要。今回はまず`slalomSequenceCheck()`側で角度可変の効果を検証してから、実際の探索走行への適用要否を判断する方針（§4 TODO参照）
- **`slalom_multi_angle`（暫定80.0→75.0に実車調整済み、要さらなる検証）の実車検証は継続中**

### 2.11 次回検討事項（設計メモ、実装は次回セッションへ、2026-09-18）

走行距離・パラメータの実車調整が一区切りついたところで、連続旋回の実運用適用について実装なしで検討した内容を記録する。

#### (a) 連続旋回の実運用適用：同方向（実質的なUターン）と逆方向（S字/斜め走行）は別物として扱う必要がある

- 両者は軌道の形が違う：逆方向（右→左など）は合計の向き変化が0°で軌道はS字（車線変更的）。同方向（右→右など）は合計180°回頭する「フック」型で、逆方向よりずっと大きく横に膨らむ
- **同方向連続旋回は既存の`uTurn()`（行き止まり用）の置き換えにはできない**：`lefthandSlalom()`/`adachiSlalom()`の行き止まり判定（`search.cpp`の該当`else`/`rear`分岐）は「左右前すべて壁」で発火するため、この分岐に入った時点で横の逃げ場が無いことが確定している。フック型の軌道は横に膨らむため、この場面では即座に側壁へ接触する。`uTurn()`（超信地旋回＋バック/前進、横方向の移動を伴わない）が唯一安全な選択肢のまま
- 同方向連続旋回が使えるのは「行き止まりではなく、経路として右折→右折（または左折→左折）が続く」場合のみ。この場合は各区画の該当方向がそれぞれ経路として選ばれている＝開いているため、横の膨らみを吸収する余地がある。ただし現状でも独立した`slalom(dir,90)`を2回呼ぶだけで動作はする。「1回の大きな旋回にまとめる」最適化には、「次も同方向に曲がる」という**先読み**が要る。
  - `lefthandSlalom()`（センサ反応型）は現在のセンサ値しか見えないため原理的に不可能
  - `adachiSlalom()`も探索中（壁が未確定）は同様に不可能だが、**既知の迷路を使う最短走行**なら`g_map.wallDataGet()`で2区画先の壁情報を先読みできるため実現可能。ただし現状`fast.cpp`の最短走行はslalomを使っておらず（`rotate()`ベース）、この最適化は「スラローム版最短走行」を新設して初めて意味を持つ（未着手）
- 逆方向連続旋回（S字）は`lefthandSlalom()`・`adachiSlalom()`どちらでも先読みなしで既に自然発生している（今のセンサ値だけで毎回判断しているため）
- `adachiSlalom()`の内部座標管理（`axisUpdate()`）は「`slalom(right,1)`→`slalom(left,1)`で横に1区画分ちょうど移動した」ことを前提にしている（各アクションで1区画分`axisUpdate()`するため）が、§2.10の実測は横0.5区画だった。**`slalom_multi_angle`で角度をさらに絞ると横移動量はさらに減り、内部座標と実位置のズレがむしろ広がる可能性がある**（`lefthandSlalom()`は絶対座標を持たないためこの影響は受けないが、壁への幾何学的な収まりの問題は残る）
- 実装前に、**前後の直進の影響を除いた「連続旋回そのものの横移動量」を測る専用テスト**が必要（現状の0.5区画という数値には助走・旋回直後の直進の長さが混ざっている）。その上で目標（`lefthandSlalom()`はセンサでの事後補正が効くので多少のズレは許容できる／`adachiSlalom()`は内部座標がズレると後続の壁判定に影響するので1区画に寄せたい、など）を決め、`slalom_multi_angle`を絞る方向と`turn_diff_max`を上げてより鋭く曲がる方向のどちらで調整するか選ぶ

#### (b) 旋回中のセンサ測定による次の壁の先読み判定

- センサ値（`sen_fr`/`sen_fl`/`sen_r`/`sen_l`）は`sensorTask`（core1、1ms周期、`sensor.cpp`）が`RUN::interrupt()`とは独立に更新し続けているため、`rotate()`/`slalom()`中でも値自体はすでに取得できている。新しく必要なのは「いつ」「どの値を」「どの閾値で」見るかという設計
- `rotate()`（その場超信地旋回）は位置が旧区画中心に固定されたまま向きだけ変わるのに対し、`slalom()`（並進を伴う旋回）は旋回終了時点でほぼ新区画に入っている（本セッションの実測より）。そのため`slalom()`終盤の読みの方が定常状態（新区画に入った直後の読み）に近いと推定される
- サンプリングは各while文内で計算済みの`turn_len`/`obj_turn`（`slalom()`）・`step_lr_len`/`obj_step`（`rotate()`）の進捗70〜90%あたりが候補（新方向への正対に近づく、かつ旋回後半は角速度が下がるためメディアン3+IIR（時定数≒3ms）の追従遅れが出にくい）
- 定常状態の`th_sen_fr/fl`は正対に近い角度を前提に校正されているため、斜め入射になる旋回中は別閾値が必要（実測での校正が要る。解析的に予測するのは難しいと想定されるため、`adcView()`のような専用診断モードで「旋回進捗%に対するセンサ値」のカーブを取ってから閾値と判定タイミングを決める進め方を想定）
- **重要な指摘（ユーザー、2026-09-18）**：早期判定結果を「情報として持っておくだけ」（判断自体は旋回完了後に従来通り行う、という保守的な使い方）にしても意味がない。`slalom()`の着地位置は理論上の区画境界からズレている（本セッションで判明した「旋回が理論位置の前後0.25区画ずつにはみ出す」ズレ、§2.8・§2.9）ため、後続の分岐が結局`straight(SECTION, ...)`のような**固定距離**の直進で実行されると、旋回中に検知していたはずの壁に、旋回終了時点（＝固定距離の直進を終えた時点）で衝突しうる。**早期判定を実際に活かすには、後続の直進距離を固定`SECTION`ではなく、検知した壁までの距離に応じて動的に決める（またはセンサ閾値超えで打ち切る）方式に変える必要がある**。これは`straight()`/`oneStep()`が現状センサを一切見ておらず、距離カウントのみで動いているという設計そのものに関わる変更になる（`RUN`クラス全体に影響する大きめの変更）

### 2.16 探索走行への0.25区画早出し補正の適用検討と`adachiSlalom()`へのハイブリッド実装（2026-09-22）

- **背景**：§2.8で判明した「`slalom()`は理論上の旋回位置の0.25区画手前から始まる」ズレを、`runSlalom()`（既知マップ）だけでなく探索走行（`lefthandSlalom()`/`adachiSlalom()`）にも補正なしで運用していたため、実車で壁への衝突が頻発した
- **検討した案**（会話内で複数案を比較）
  1. 全ての直進を一律0.25区画短くする → **却下**。直進が2区画以上連続する場面で短縮が毎回積み重なり、区画境界からの累積ズレが際限なく増える。`REF_SEN_*`/`TH_SEN_*`は区画中央を前提に校正された値のため、繰り返し中心からズレた位置でのセンサ判定は誤検知リスクが上がる
  2. 旋回中センサ先読み＋動的打ち切り（`straight()`/`oneStep()`を固定距離からセンサ応答に変える） → 理想だが`RUN`全体に影響する規模の改修のため今回は見送り（§4.4参照、引き続き将来課題）
  3. **既知壁のみのハイブリッド先読み（採用）**：次に向かう区画の壁が既に`g_map`に記録されている場合に限り、`runSlalom()`と同じ0.25区画早出し補正を適用する。未知の場合は補正なしで1区画進み、その場でセンサ判断する（今までと同じ動作）
- **`lefthandSlalom()`（モード5）は対象外に決定**：自己位置・壁情報を一切管理しないステートレスな左手法のため、「次の区画の壁が既知かどうか」を判定する材料（`g_map`の座標・壁データ）がそもそも存在せず、ハイブリッド先読みを組み込めない。衝突が実際に起きている状態を放置できないため、**90度旋回を`slalom()`から`rotate()`へ撤回**（`lefthand()`と同じ動作に戻す）。行き止まりの`uTurn()`のみ据え置き、これが`lefthand()`との唯一の違いとして残る
- **`adachiSlalom()`（モード6）に実装**
  - `SEARCH::peekKnownNextDir(after_dir, gx, gy)`（`search.cpp`、新規private）を追加。`after_dir`向きに1区画進んだ先の区画を仮定して`g_map.mypos`を一時的に動かし、その区画の東西南北4方向の壁が全て`_UNKNOWN`でないことを確認した上でのみ`g_map.nextDirGet()`を呼んで先読みし、元の位置に戻す。壁が未知なら`loca_dir_error`を返し、呼び出し側は先読みを信用しない
  - 先読みの正しさの根拠：先読み対象区画の壁が既に既知（`_UNKNOWN`でない）であれば、実際にそこへ到達して`wallSet()`を呼んでも`g_map`の状態は変化しない（既知の値を再度同じ値で上書きするだけ）。先読み時点から実到達時点までの間に他の区画のセンシングは発生しないため、`g_map`全体が凍結された状態で`nextDirGet()`を2回呼ぶことになり、既知区画に限れば先読みと実判断は必ず一致する。逆に壁が未知の場合、実到達時に`wallSet()`が`_UNKNOWN`を実際の値で更新するため、先読み時点の（未知を通行可能とみなした）判断と食い違う可能性があり、信用できない
  - `adachiSlalom()`のループの`case front`を変更：`peekKnownNextDir()`で次の区画の判断が`right`/`left`（＝既知の旋回）と分かった場合のみ、`oneStep()`の距離を`SECTION - SECTION*0.25`に短縮。それ以外（`front`/`rear`/先読み不可）は従来通り`SECTION`丸ごと進む
  - 探索の往路（1周目、壁がほとんど未知）ではこの補正はほぼ発動せず、既存動作（無補正、衝突リスクが残る）のまま。復路（ゴール→スタート、既に往路で解明した区画を通る）や、同じ区画を再訪する場面で補正が発動し始める設計
  - `rear`（行き止まり、`uTurn()`）はこの先読みの対象外（`uTurn()`は超信地旋回ベースで0.25区画早出しの影響を受けないため）
- **実車確認は未実施**。往路での衝突リスクは残ったままのため、往路自体の安全性向上（Plan 4：旋回中センサ先読み＋動的打ち切り、§4.4）は引き続き別課題として残る

### 2.17 基板接触不良によるフェイルセーフ2件の追加（2026-09-22）

- **背景**：スラローム中の壁衝突で基板の接触が悪くなると、(a) 該当箇所の壁検出用SLEDが暗くなる、(b) モード用LEDが`0x0a`/`0x05`交互点滅する、(c) スラロームの回転が止まらなくなる、という症状が実車で報告された。(b)は`map_manager.cpp`の`nextDirGet()`/`nextDir2Get()`にある「ゴール到達不能」判定の`while(1){ledSet(0x0a);delay(500);ledSet(0x05);delay(500);}`と完全に一致するビットパターンで、このリポジトリ内で同じパターンを使っている箇所は他に無い。(c)は`slalom()`/`rotate()`の旋回終了判定が`TMC5240::readXactualLR()`/`readXactual()`（TMC5240とのSPI通信で実パルス数を読む）に依存しており、この通信経路の接触不良でパルス数が更新されなくなると`turn_len > obj_turn`（`slalom()`）や`step_lr > obj_step`（`rotate()`）が成立せず`while(1)`が終わらなくなることが原因と推定される。いずれも今回追加した機能固有の不具合ではなく、以前から存在する「エンコーダ/センサ読み取りがおかしくなったら永久に待ち続ける」設計上の弱点で、衝突が増えたことで顕在化した
- **対策1: `RUN::rotate()`/`RUN::slalom()`にタイムアウトを追加**（`run.cpp`）：関数開始時の`millis()`を基準に、`TURN_TIMEOUT_MS`（`parameter.h`、3000ms）を超えたら`stepGet()`/`stepGetLR()`ベースの判定を諦めて`break`する`timed_out`フラグを両方の`while(1)`ループに追加。`rotate()`はタイムアウト時も含め最終的に必ず`stop()`を呼ぶ（元々の終了処理と同じ）。`slalom()`は通常は停止せず次の動作へ速度を繋ぐ設計だが、タイムアウト時のみ例外的に`stop()`で強制停止する（`slalom180()`は`slalom()`のラッパーのため自動的に同じ保護を受ける）。どちらもタイムアウト時は400Hzのブザーを200ms鳴らして異常を知らせる
- **対策2: `nextDirGet()`/`nextDir2Get()`の到達不能判定にスイッチでの脱出を追加**（`map_manager.cpp`）：`while(1)`を`while(switchGet()==0)`に変更し、ループ内で`motorDisable()`を呼びながら点滅を続け、スイッチが押されたら`loca_dir_error`（既存の`t_local_direction`のエラー値を流用）を返すようにした
- **対策2に伴う呼び出し元4関数の修正が必須だった理由**：`nextDirGet()`/`nextDir2Get()`が`loca_dir_error`を返すだけで呼び出し元のswitch文（`front`/`right`/`left`/`rear`のみ、`default`無し）が対応しないと、`glob_nextdir`が前回の値のまま`g_map.axisUpdate()`が呼ばれ続け、`mypos.x`/`mypos.y`（`unsigned char`）が境界チェックなしに増減し続けて配列外アクセスに至る危険があった。そのため`adachi()`・`adachiSlalom()`（`search.cpp`）・`FAST::run()`・`FAST::runSlalom()`（`fast.cpp`）の計4関数、各2箇所（開始直後の方向合わせ・メインループ内）に`case loca_dir_error: return;`を追加し、安全に呼び出し元へ制御を戻すようにした（`motorDisable()`は`nextDirGet()`/`nextDir2Get()`内で既に実行済みのため追加の後処理は不要）
- **既知の制約**：スイッチで抜けた後、呼び出し元の関数はその場で`return`するのみで、`misc.cpp`の`modeExec()`が期待する「ゴール到達済み」等の後処理（`goalAppeal()`・`mapWrite()`等）は実行されない。あくまで「無限に固まらず安全にモータを止めて関数を抜けられる」ところまでの対応であり、迷路情報の保存等は行われない点に注意（→§2.53で、脱出後は往路・復路に関わらず`modeExec()`の残りを中断してモード選択へ戻るようにした）
- **実車確認は未実施**。`TURN_TIMEOUT_MS`（3000ms）は実測に基づく値ではなく、明らかに異常と判断できる余裕を持たせた暫定値のため、正常系の最も遅いケース（低速パラメータでの180°`slalom180()`等）を誤検知しないか確認が必要

### 2.21 `straightSensorDiag()`が自分自身の閾値で早期停止してしまい、壁付近のカーブが取れない問題を修正（2026-09-23）

### 2.22 `th_approach`実測データの取得と評価：プレースホルダ値のままで安全マージンありと判明（2026-09-23）

- **背景**：§2.21の修正後、`straightSensorDiag()`を段階的に（`section_check=2`→`2.2`）実行し、壁近傍まで含む`fr`/`fl`のカーブを実測した。スタート位置（機体後部を後ろ壁に接触させた状態の機体先端）から壁までの実測距離は**580mm**
- **タイヤ直径未較正の影響**：`TIRE_DIAMETER`は`TIRE_DIAMETER_INIT`(47.5mm)のまま未調整。`len`はこの値を使ったパルス→mm換算のため、実距離とズレている（実測では`len`が実距離を過小に見積もる方向、すなわち実際のタイヤ径は仮定より大きい可能性が高い）。ただし **`th_approach`はセンサ生値そのものを見る閾値なのでこのズレの影響を受けない**。`len`軸の目盛りが不正確なだけで、`fr`/`fl`の値自体は物理的に正しいデータとして使える

### 2.34 連続旋回のNG局面(U字・S字3回)だけ旋回半径を絞る（モード9、2026-09-24）

- **実車確認結果**（§2.32適用後のモード9）：OK＝単体のスラローム・異方向2回(S字)。NG＝同方向2回(U字)・異方向3回。**いずれも最後のカーブで曲がり切れず側壁へ衝突**
- **推定原因**：`slalom()`の旋回半径は`R≒slalom_speed×tread_width/(2×turn_diff_max)`≒250×66.1/(2×75)≒110mm。隣り合う区画で連続して曲がる経路は1区画(180mm)ずつ進むため、理想は半径≒90mmの1/4円弧の連続。U字は横移動が円弧2回分(2R)で、R=110では約220mmとなり通路幅180mmに収まらない。異方向でも3回続くと1回あたり約20mmの超過が累積して3回目に外側の壁へ当たる。§2.32の角度絞りだけでは半径超過は解消しない。単体・S字2回はOKのため、R自体は変えず連続旋回のうちNGの局面だけ対処する方針（ユーザー判断で確定）
- **実装**
  - `RUN::slalomProbe()`に`tight`引数を追加（`run_dynamic.cpp`、`run.h`）。`true`のとき`slalom_speed`/`turn_diff_max`を実車調整済みの`slalom180_speed`(250)/`slalom180_diff_max`(95)へ一時差し替えて旋回する(`slalom180()`と同じ一時差し替え、旋回後に復元)。95では`R≒87mm`。新パラメータは追加していない
  - `adachiSlalomDynamic()`が直進を挟まない連続旋回の回数`chain_len`と直前の旋回方向`prev_turn_dir`を管理し、`tight`＝(連続旋回の3回目以降)または(2回目かつ直前と同方向=U字)のとき`true`を渡す。`case front`/`case rear`で連鎖は破棄。OKの異方向2回(S字)と単体は従来通り
- **留意点**：`slalom180_diff_max`を変えると`slalom180()`(最短走行モード7の`rear`・調整モード7)にも影響する。§2.32の角度絞りは併用（U字2回目は`90+15=105°`を半径87mmで旋回）
- **実車確認**：未実施。U字・異方向3回で最後のカーブが曲がり切れるか、S字2回・単体が影響を受けていないかを確認する。不足する場合は`slalom180_diff_max`の増減、または`tight`の適用範囲(2回目以降すべて等)の見直しを検討する

### 2.35 §2.34の実車確認結果：異方向2回・3回はOK、U字は未解決のためU字専用の速度差`slalom_u_diff_max`を新設（2026-09-24）

- **実車確認結果**：§2.34適用後、異方向の連続旋回(S字)は2回・3回とも曲がり切れた。**同方向2回(U字)は依然として曲がり切れない**
- **推定原因**：診断ログ(§2.31、右旋回90°で約758ms)から旋回中の平均半径を見積もると、経路長≒平均速度(350→250へ減速)×時間≒216mmを旋回角π/2で割って**R≒137mm**（旋回開始直後の速度が高く、`R=v×tread/(2×turn_diff)`の計算値110mmより大きい）。U字の1回目は前壁検知で75°へ絞られたあと半径のままの緩い円弧(横移動≒`R(1-cos75°)`≒101mm)で、2回目を`slalom180_diff_max`(95、R≒100mm)の105°で回っても横移動の合計が`101+1.259R`≒227mmとなり、U字の脚の間隔180mmに対して約47mm超過して外側の壁に当たる。1回目の横移動が既に確定しているため、2回目でこれを吸収するには半径をさらに絞る必要がある（脚間隔180mmから逆算すると`1.259R≒180-101`でR≒63〜75mm、`turn_diff_max`換算で約125）
- **対策**：U字(同方向連続旋回の2回目)専用の左右速度差ピーク値`slalom_u_diff_max`を新設（`parameter.h`の`SLALOM_U_DIFF_MAX_INIT`=125、`RUN`メンバ、`Flash.cpp`(`flashInit()`/`paramWrite()`/`paramRead()`、`paramRead()`ではループ前にデフォルト代入)、`webserver.cpp`の`Slalom U diff max`欄。Web UIで再コンパイルなしに調整可）。`RUN::slalomProbe()`の第4引数を`bool tight`から`float tight_diff_max`（>0でその速度差ピーク値と`slalom180_speed`で旋回）へ変更。`adachiSlalomDynamic()`は「連続旋回の2回目以降で直前と同方向」なら`slalom_u_diff_max`、そうでなく連続3回目以降なら`slalom180_diff_max`を渡す。異方向の連続と単体は§2.34から変わらない
- **実車確認**：未実施。U字で曲がり切れるかを確認し、`slalom_u_diff_max`をWeb UIで調整する（増やすほど半径が小さくなる。大きすぎると内側の車輪が`MIN_SPEED`に張り付き外側だけ速くなって姿勢が乱れやすい、§11参照）。1回目の旋回の緩さが根本原因のため、調整で解決しない場合は1回目の旋回自体を(U字か否かの先読みが不能なため)常に絞る等の別案が要る

### 2.43 `slalom180()`の配線ミスを修正：行き止まりはuTurn()、同方向連続旋回(フック/U字)をslalom180()に（2026-09-24）

- **実車確認**：未実施。同方向連続旋回で`slalom180()`が発動し`slalom180_diff_max`(§2.42で140に変更)の効果が確認できるか、3回以上連続する場合のペア分割が破綻しないかを確認する必要がある

- **対応**（原因不明のまま、期待する挙動を全モード共通で保証する形）：`MISC::modeExec()`の先頭で`mode_select = mode`と記録し、末尾で`ledSet(mode)`により走行中のLED表示を実行したモード番号へ戻す
- **副次修正**：`mapWrite()`/`mapCopy()`がファイルを開けないときに割り込みを止めたまま早期`return`していたのを、再開してから`return`するよう修正

### 2.47 モード8の最初の旋回が早い問題を修正：助走短縮分をスタート直後の距離基準の動作に足す（2026-09-25）

### 2.60 速度を上げたスラロームが曲がり切れない（STEP8・STEP9、2026-09-27）

- **症状**：STEP9で`search_speed` 350→600、`slalom_speed`/`slalom180_speed` 260→400に上げたところ、`runSlalom()`などスラロームを使う走行で曲がり切れない
- **原因**：`slalom()`の旋回半径は`r = (tread_width / 2) × 並進速度 / turn_diff`（角速度が`2 × turn_diff / tread_width`のため）。`turn_diff_max`等を据え置いたまま`slalom_speed`を上げたので、半径が約1.54倍になった
  - 90°：260/70でr≈125mm → 400/70でr≈193mm
  - 180°：260/110でr≈80mm → 400/110でr≈123mm（区画中心どうしのUターンはr=90mm）
  - さらに`slalom()`は呼ばれた時点の速度（`straight()`を終えた`search_speed`）から`search_accel`で`slalom_speed`まで減速しながら曲がる。`turn_diff`は数十msで最大になるのに、600→400の減速には約130msかかり、曲がり始めはr≈290mmで膨らむ
- **対策1（STEP9の`parameter.h`）**：diff_max系を速度比（400/260≈1.54倍）で上げ、半径を調整時の値へ戻した。`TURN_DIFF_MAX_INIT` 70→108、`SLALOM180_DIFF_MAX_INIT` 110→170、`SLALOM_U_DIFF_MAX_INIT` 150→230、`SLALOM_U_MID_DIFF_MAX_INIT` 110→170。STEP8は`slalom_speed` 260のままなので変更なし。Flashに保存済みの値が優先されるため、反映にはWeb UIで入れ直すか`flashInit()`が必要
- **対策2（`fast.cpp`の`runSlalom()`、STEP8・STEP9）**：旋回前の`straight()`の終了速度を`search_speed`から旋回速度（次が`slalom180()`なら`slalom180_speed`、それ以外は`slalom_speed`）にした。減速を直進中に済ませ、旋回は最初から設定どおりの半径で曲がる。そのため`peekNextDir()`を`straight()`の前に移した
- **未対応**：モード9（`adachiSlalomDynamic()`）は`oneStepDynamic()`の等速`search_speed`のまま旋回に入るので、曲がり始めの膨らみが残る。旋回が区画境界で決まるため、事前に減速するには構造の変更が要る。最初の助走直後の`oneStep(start_short, search_speed)`から旋回する場合も同じ
- **注意**：内輪の速度`slalom_speed - diff`が`MIN_SPEED`(30)を下回ると下限に張り付くため、diff_maxは`slalom_speed - 30`以下にする（400なら370）
- **実車確認**：未実施

### 2.65 スラロームを「内輪を落とす小回り」にし、区画境界から区画境界の動作にする（STEP8・STEP9、2026-09-29）

- **要望**：旋回範囲を小さくし、中心付近で内輪の速度を落とす方式にしたい。連続旋回で旋回半径を切り替えるなどの余計な処理をなくしたい。外輪の増速も必要になるかもしれないのでパラメータにしたい
- **これまでの問題**：旧`slalom()`は並進速度を保ったまま左右に同じ速度差`turn_diff`をつけていた。半径が「速度 ÷ 速度差」で決まるため、速度を変えるたびに diff_max 系を合わせ直す必要があった（§2.60）。旋回中に減速すると膨らんだ。さらに1回の旋回が区画に収まらず、連続旋回では角度の絞り（§2.10・§2.32）、U字・3回目以降の半径の絞り（§2.34〜§2.38・§2.51・§2.54）、前壁なしの早出し（§2.52）、最短走行の0.25区画早出しと先読み（§2.8・§2.15・§2.16）、180°専用の`slalom180()`（§2.14・§2.43）が積み重なっていた
- **新しい`slalom(dir, angle)`**（`run.cpp`）
  - 外輪 = 速度 × (1 + `slalom_outer_gain` × f)、内輪 = 速度 × (1 − (1 − `slalom_inner_ratio`) × f)。`interrupt()`の`turn_enable`分岐で計算する
  - 旋回の強さ f（`turn_f`）は旋回ループが外輪の走行距離から決める。入口では外輪が`slalom_ramp_len`[mm]走る間に 0→1（下限`SLALOM_F_MIN` 0.05、0だと回り始めないため）。残りの角度が入口で使った角度と等しくなったら、同じ傾きで下げる（前後対称。§2.66で走行距離基準の台形に変更）。旋回角は `(右輪距離 − 左輪距離) / tread_width` で判定する
  - 軌跡は走行距離だけで決まり、速度にも旋回中の減速にもよらない。並進速度は旋回中に`slalom_speed`まで下げる（これまでどおり）
  - 当初は f を旋回角に対して直線的に上げる案だったが、数値計算すると曲がり始めの半径が大きすぎて張り出しが100mmを超えた（`k_min` 0.2・30°で約160mm）。外輪の走行距離に対して上げる（クロソイド）と、`k_min` 0.1・30mmで約57mmに収まる
- **`slalomParamUpdate()`**：形状パラメータの範囲チェックをし、同じプロファイルを数値積分して90°旋回の張り出し`slalom_offset`（区画中心から旋回の開始点・終了点までの距離）を求める。前後対称なので前方向と横方向の張り出しは等しい。パラメータの読込時・Web保存時に計算し、Serialと Web UI に表示する

| `slalom_inner_ratio` | `slalom_ramp_len` | `slalom_outer_gain` | `slalom_offset`（tread 67.5mm） |
| --- | --- | --- | --- |
| 0.0 | 20 | 0.0 | 約44mm |
| 0.1 | 20 | 0.0 | 約52mm |
| 0.1 | 40 | 0.0 | 約62mm |
| 0.1 | 40 | 0.3 | 約58mm |
| 0.2 | 40 | 0.0 | 約71mm |
| 0.3 | 60 | 0.0 | 約94mm（区画に収まらない） |

- **`slalomCell(dir)`**：区画境界から次の区画境界までを1動作にする。`oneStep(HALF_SECTION − slalom_offset)` → `slalom(dir, 90)` → `oneStep(HALF_SECTION − slalom_offset)`。カウンタは`stay()`と`slalom()`でクリアされるので§2.9の前提は保たれる。呼ぶ側は区画境界で呼ぶだけでよく、U字は2回続ければよい
- **呼び出し側**
  - `FAST::runSlalom()`（モード7）：`run()`と同じ骨組みにし、旋回は`straight(…, 終了速度 slalom_speed)` → `slalomCell()`。行き止まりは`uTurn()`。ゴール・行き止まりの前の直進は`stoppableSpeed(HALF_SECTION)`で終える。`peekNextDir()`・`start_short`は削除

### 2.66 スラロームの f を走行距離で前後対称な台形にする（STEP8、2026-10-19）

- **動機**：`slalomCell()`は旋回の前後に同じ長さ`HALF_SECTION − slalom_offset`だけ直進するので、旋回の前方向の張り出しと横方向の張り出しが等しい必要がある。§2.65の出口は「残りの角度が入口で使った角度と等しくなったら f を下げ始める」という角度基準だった。旋回の終わりは f が小さく、ほとんど曲がらずに横へ進むので、角度がわずかにずれるだけで終点が大きく動く。`slalomParamUpdate()`と同じ刻み0.1mmで数値積分すると、前方向56.4mmに対して横方向は54.1mmになり、刻みを0.001mmにすると56.4mmになった（刻みで2mm変わるほど敏感）
- **参考**：kerislabのスラローム軌道設計の記事（[①](https://www.kerislab.jp/posts/2020-04-25-slalom-trajectory-1/)〜[④](https://www.kerislab.jp/posts/2020-04-25-slalom-trajectory-4/)）。角速度の形を事前に決め、前後の直線長を幾何で求める方式
- **実装内容**（`run.cpp`/`run.h`）
  - `slalomProfile(s_out, s_total, ramp_len)`：状態を持たない関数にした。f = max(`SLALOM_F_MIN`, min(1, s/L, (S − s)/L))。S は旋回全体の外輪の走行距離、L は`slalom_ramp_len`。入口と出口が同じ傾き・同じ下限なので、f は距離について前後対称になる
  - `slalomRampAngle(s_end)`：入口ランプで外輪が 0→s_end 走る間の旋回角。外輪1mmあたりの旋回角は g(f)/tread（g(f) = (外輪 − 内輪)/外輪 = a·f/(1 + b·f)、a = gain + 1 − ratio、b = gain）で、f = s/L の区間は解析的に積分できるので数値積分しない
  - `slalomLength(obj_th)`：任意の角度の S を求める。台形（obj_th ≥ 2·`slalom_ramp_th`）なら旋回角が S の一次式になるので `S = 2L + (obj_th − 2·ramp_th)·tread / g(1)` で直接求める。入口と出口のランプだけで曲がりきる三角形（小さい角度や長いランプ）は二分法（30回）で求める。旋回の開始時に呼ぶ
  - `slalom(dir, angle)`：開始時に`slalomLength()`で S を求め、f を`slalomProfile()`で決める。終了判定はこれまでどおり旋回角。実機の遅れで角度が足りないときは、S を過ぎても f = `SLALOM_F_MIN`で回り続けて角度を合わせる
  - `slalomParamUpdate()`：`slalom_ramp_th`（入口ランプで曲がる角度）を求め、90°の S で軌跡を積分する。Serialに`slalom_offset`（前方向）と横方向の張り出し、S を出す（横方向は対称性の確認用）
  - `slalomCell()`は変更なし
- **数値検証**（Python、tread 67mm・`slalom_inner_ratio` 0.1・`slalom_outer_gain` 0）
  - 90°：L = 10/30/60/100/150mm で、前方向と横方向の差は0.1mm以内（L = 30mm で56.40/56.43mm）。刻み0.1mmと0.01mmで結果は同じ
  - 任意の角度（L = 30mm、`slalom_ramp_th` 11.57°）：旋回前と旋回後の直線の延長が交わる点までの距離は、20°（三角形）で22.18/22.18mm、45°で32.11/32.12mm、135°で115.02/115.03mm。180°は前後方向のずれ0.00mm
  - `slalomRampAngle()`の解析積分は`slalom_outer_gain` 0/0.5/0.2 の3通りで数値積分と1e-5 rad以内で一致した
- **実車確認**：未実施。STEP9へは実車確認後に移植する

### 2.71 内輪がMIN_SPEEDで頭打ちになり、スラロームの出口が前に出る（STEP8、2026-10-26）

- **症状**：調整モード3（`circuitCheck()`）で、最初の角は正しく曲がるが、2つ目以降の角では半区画近く進んでから曲がる
- **原因**：`slalom_speed` 260・`slalom_inner_ratio` 0.1では、旋回の中央で内輪が26mm/sになる。`interrupt()`の最後で`MIN_SPEED`（30）に持ち上げられるので、左右の速度比が設計からずれ、中央での旋回の強さが0.9から約0.885に落ちる。その結果、外輪が`s_total`を走り切った時点で90°に約1°足りない。残りは`SLALOM_F_MIN`（外輪1mmあたり約0.04°）で回るので、ほぼ直進で約30mm余計に進む。旋回の出口が次の辺の方向へ前に出るので、次の角が遅れる。入口は正しいので、1つ目の角だけは正しく見える
  - カウンタの引き継ぎ（§2.9）とコースの幾何も確認したが、ずれる要素はなかった
- **実装内容**
  - `RUN::interrupt()`（`run.cpp`）：スラローム中に内輪が`MIN_SPEED`を下回るときは、左右に同じ倍率`k = MIN_SPEED / 内輪`を掛ける。軌跡は左右の速度比だけで決まるので、`slalomParamUpdate()`の計算どおりになる。その間は並進速度が上がる（上の設定では外輪が260→約300mm/s）
  - `SLALOM_MIN_SPEED_SCALE_MAX`（`parameter.h`、2.0）：`k`の上限。`slalom_inner_ratio`が0付近のとき、倍率が際限なく大きくなるのを防ぐ。`slalom_speed × slalom_inner_ratio`が15mm/s未満だと、上限にかかって比が保てなくなる
  - `RUN::slalom_tail`（`run.h`）：直前の`slalom()`で、外輪が`s_total`を超えて走った距離[mm]。`slalom()`の終わりに記録する
  - `circuitCheck()`（`adjust.cpp`）：角を曲がった後、`slalom_tail`をLEDの点灯数で次の角まで表示する（5mm未満で1個、20mm未満で2個、45mm未満で3個、45mm以上で4個）。直進中・旋回中のLED表示（`0b0001`／`0b0010`）は出さないようにした
- **実車確認**：修正前はLEDが3個（20〜45mm）、修正後は1個（5mm未満）になった（2026-10-26）
- **未解決点**：STEP9へは、STEP8の調整がすべて終わってからまとめて移植する
